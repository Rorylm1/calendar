# Personal calendar service

Private Gmail-first backend for the Edge calendar interface. Runs on Node 24.13+ using Fastify, Node's built-in SQLite, Google OAuth, and Gemini models through OpenRouter's Responses API. The frontend integration contract is in [API.md](API.md).

## Run locally

1. Install with `npm install` inside this directory.
2. Copy `.env.example` to `.env` if no local configuration exists. Set two independent secrets: `CALENDAR_SERVICE_TOKEN` needs at least 32 characters; `CALENDAR_ENCRYPTION_KEY` needs exactly 32 random bytes encoded as 64 hex characters or base64. Keep this file private and never commit it.
3. Run `npm run dev` (reloads on code changes) or `npm start`. Both load `.env`. The service defaults to `127.0.0.1:8787`; `GET /health` does not require a credential.
4. The frontend authenticates its owner and proxies requests with the service token. Never put that token in a public environment variable or client bundle. Configure its backend URL to this local service.
5. Run `npm run typecheck` and `npm test`. The tests use temporary/in-memory databases, synthetic email, mocked Google/model responses, and no real mailbox or API key.

The application can serve manual calendar operations before Gmail and OpenRouter are configured. It starts with an empty calendar; no fictional bookings are inserted into personal data.

## Connect Gmail

Create a Google Cloud OAuth **Web application** client, enable the Gmail API, and configure this exact local redirect URI: `http://localhost:3000/api/calendar/gmail/callback`. Set the client id/secret in `.env`. Set `GMAIL_ALLOWED_EMAIL` to the original/default mailbox (the example address is a placeholder). Additional inboxes are connected explicitly from Connections with their requested email address. That address is bound to the OAuth state and checked against Gmail’s actual profile; choosing a different address is rejected without disturbing an already connected inbox.

The frontend calls the connect route with the authenticated owner's stable id, keeps the returned state in an HttpOnly SameSite=Lax cookie, and verifies it before forwarding the callback. The backend independently checks its expiring single-use state and PKCE verifier. Tokens stay encrypted on the service. Authorization requests only `gmail.readonly`, offline access, and fresh consent. Each inbox has separate encrypted tokens, history/checkpoints and hourly scheduling. Reconnect errors are visible per inbox; disconnect revokes only that inbox’s grant when possible and deletes only its local tokens and captured source content. Confirmed events and proposal evidence remain in the calendar.

For personal use, configure the Google OAuth consent/publishing setup deliberately. An external app left in Testing generally receives refresh tokens expiring after seven days for these scopes. Read the current [Google OAuth guidance](https://developers.google.com/identity/protocols/oauth2/web-server) and [restricted-scope personal-use exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification). This code does not complete account-holder consent or demonstrate production approval.

## Capture and interpretation

An initial scan covers the previous 30 days, including Promotions/Updates/Social and sent mail; only spam, trash, and drafts are excluded. Subsequent scans use Gmail history. Each bounded page and the remaining message ids are saved, individual messages are fetched into the encrypted processing queue, and only then is the history checkpoint advanced. Saved batches resume after interruption. Expired history causes a bounded recovery and a visible warning about older possible gaps. See [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync).

The scheduler checks Gmail hourly, with a separate explicit Check now route. Capture yields after 20 pages or approximately 90 seconds of work; an in-flight request and its bounded retries can finish after that time limit. A successful partial import automatically continues its saved scan after processing the current batch, with a visible import-in-progress warning. This resumes the same bounded query rather than starting another mailbox check. Capture continues even when the AI budget is paused. A failed batch waits for the next hourly or manual check. Overlapping checks coalesce, including a Check now requested during interpretation.

All Gmail reads share a one-request-per-second pacer by default (`GMAIL_REQUEST_INTERVAL_MS=1000`). The [current Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota), checked on 7 September 2026, give new projects 6,000 units per minute per user: message reads cost 20 units, thread reads 40, attachment reads 20, list reads 5, history reads 2, and profile reads 1. The configured project's console also shows the 6,000-unit limit. Default pacing stays below 2,400 units per minute even if every call reads a thread. Transient errors retry at most twice; quota responses wait at least 60 seconds between attempts. Disconnect and shutdown cancel active reads, quota waits, and interpretation requests; interrupted work remains pending, and uncertain model cost reservations remain conservative. Exhausted retries preserve progress and a safe phase/status diagnostic, without retaining provider error bodies.

Interpretation drains eligible work in separate batches of 100, without additional mailbox polling. Fresh captures take priority over retries. Failed interpretation backs off, stops automatically after three attempts, and remains visible for an explicit retry through `POST /v1/gmail/retry-processing`. Thread context includes up to eight recent messages, including sent replies. Markup and tracking links are removed; quoted replies are removed when the quoted text is already available in supplied context, while forwarded content is preserved. Detached text bodies are fetched within a size cap. Individual message text is capped at 9,000 characters and each context message at 1,600.

Interpretation uses `google/gemini-3.5-flash-lite` for content triage and `google/gemini-3.6-flash` for full extraction. Set `OPENROUTER_API_KEY`, `AI_TRIAGE_MODEL`, and `AI_EXTRACTION_MODEL`; only the explicit OpenRouter key enables model calls. The OpenAI-compatible SDK is used with a fixed `https://openrouter.ai/api/v1` base URL, so that key is never sent to OpenAI's endpoint. Changing a model also requires explicitly configuring its input/output token prices so budget accounting remains meaningful. Prompts are concise and generic; there are no sender/domain or booking-keyword gates. Uncertain triage goes to extraction. A recent encrypted triage audit is available at `GET /v1/gmail/triage` so filtered decisions can be inspected.

Requests use OpenRouter's [stateless Responses API](https://openrouter.ai/docs/api/reference/responses/overview) with `store:false`, a strict JSON schema, and no tools. [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) requires parameter support (`require_parameters:true`), disallows collecting providers (`data_collection:deny`), and caps provider prices at the configured rates. If no eligible endpoint exists, processing fails visibly rather than weakening these restrictions. [Structured-output support](https://openrouter.ai/docs/guides/features/structured-outputs) varies by endpoint, so application validation remains in place. The routing policy restricts providers according to OpenRouter's published data-policy information; it is not an independent guarantee about every provider's retention practices.

Default USD prices per million tokens are $0.30 input / $2.50 output for Gemini 3.5 Flash Lite and $0.75 / $3.75 for Gemini 3.6 Flash, checked against [OpenRouter's model catalog](https://openrouter.ai/api/v1/models) on 7 September 2026. The monthly default budget is $5. Each request reserves a conservative upper bound before it runs, then settles using the provider's reported cost when available, otherwise its token counts and configured rates. Token/cost summaries are stored without prompts. An uncertain network outcome keeps its reservation; this can pause processing earlier than the actual provider bill. Missing API keys or exhausted budgets pause interpretation while preserving captures.

Two explicitly authorized live smoke calls used invented booking text only. Both exact models accepted the strict/private routing settings, and extraction returned the correct date, time, and reference. Provider-reported total cost was **$0.00507645**; the separate smoke ledger and token counts are written locally to `smoke/openrouter-smoke.json`. No Gmail or personal database was accessed. This confirms API compatibility, not real-mail interpretation quality. To rerun only when paid API use is authorized: `RUN_LIVE_MODEL_SMOKE=yes node --env-file=.env --import tsx scripts/smoke-openrouter.ts`.

Valid dated bookings and invitations are applied automatically, while missing or conflicting facts remain pending. Invitations use the INVITATION: prefix in the web calendar and private iPhone feed. Exact supporting excerpts are checked against source text. Database transactions make confirmation idempotent and prevent stale proposals from overwriting later manual edits. Missing dates require correction; missing times remain absent. Multi-leg journeys remain separate. A single non-recurring ICS attachment is parsed into context; unsupported attachment-only messages become clearly incomplete review items. WhatsApp JPEG/PNG screenshots are supported. Gmail image/PDF attachments, voice notes and recurring-calendar extraction remain unsupported.

Both interpretation stages distinguish proof of spending from a commitment: a receipt for a completed purchase/visit produces no event, while a payment receipt establishing a reservation, ticket or scheduled service remains relevant. The service date takes precedence over the payment timestamp. This distinction is applied generally, without venue-specific filtering. Three synthetic live checks cover a pub purchase, restaurant deposit and train-ticket receipt; the pub case is also passed directly to extraction to cover a previously cached triage decision. Results are written locally to `smoke/receipt-check.json`. The six calls cost $0.01664445 and did not rescan Gmail. Repeat only when live model use is authorized: `RUN_LIVE_MODEL_SMOKE=yes node --env-file=.env --import tsx scripts/check-receipts.ts`.

## Storage and operations

Sensitive data, including OAuth credentials, source text, event details, proposals, and evidence, uses AES-256-GCM with a fresh nonce and record-bound authentication. The encryption key is separate from the SQLite file. The service sets a restrictive file mask; the database has mode 0600. Encrypted SQLite data and WAL still require an appropriate backup policy. Back up the encryption key separately: losing it makes stored calendar data unreadable. No provider responses, OAuth codes, request bodies, or authorization headers are logged.

Completed source bodies and triage excerpts are removed after 14 days, even if Gmail needs reconnecting. Pending or failed captures remain until handled; proposal evidence remains for review. Message ids and processing status support deduplication. Run one service process per database; an in-process lock prevents concurrent synchronization, but this version is not a distributed worker system. Node 24 currently prints an experimental-feature notice for its built-in SQLite API; the tested runtime is Node 24.13.0.

The backend is deployed on Hetzner with the private Next.js frontend on Vercel; authenticated access, trusted TLS, and database persistence through restart have been verified separately from the tests. See [deployment notes](../ops/README.md) and [Google setup](../ops/google-setup.md). The allowed Gmail account is connected, the initial import is complete, and hourly capture is active. Failed interpretations remain available for retry. Real-mail quality and iPhone acceptance remain separate checks. The private ICS feed and opt-in web push are implemented; actual iPhone refresh and notification delivery remain device acceptance checks.

## WhatsApp capture

The official Cloud API webhook verifies exact-body signatures and restricts the sender and receiving number before encrypted durable capture. Text and supported JPEG/PNG screenshots are interpreted when processing is enabled. Clear event names and dates are sufficient; supplied descriptions and locations are retained. Optional hidden descriptions do not block extraction. Missing required dates need clarification. The image-access token stays private, and the application sends no WhatsApp replies. A real screenshot has passed download, interpretation, automatic invitation creation and private ICS export. See [the implementation and acceptance record](../docs/whatsapp-spike.md).
